## 策划结论

第三册的核心任务不是让零基础读者记住一组 Docker 命令，而是帮助读者建立一套不会
因为“容器能跑起来”就误判为“服务已经安全可用”的操作模型：

```text
理解镜像与容器
→
从官方软件源安装 Docker Engine
→
运行、查看、停止和删除容器
→
理解端口发布与暴露范围
→
理解数据为什么不能只留在容器里
→
用 Compose 保存一套可重复执行的服务配置
→
查看状态与日志
→
完成更新、备份、恢复和清理
→
带着可维护的 Compose 项目进入后续各册
```

全书采用“一个持续演进的练习项目 + 少量独立验证命令”的方式：

- `hello-world` 只用于确认 Docker Engine 能正常拉取并运行镜像；
- 一个小型 Web 服务贯穿端口、目录映射、Compose、日志、更新和备份章节；
- 优先使用 Docker Official Image，不依赖来源不明的镜像或安装脚本；
- 先从服务器本机的 `127.0.0.1` 验证，再解释何时以及为什么向公网发布端口；
- 所有可能删除容器或数据的命令，在执行前明确说明影响范围和恢复条件；
- 使用 HTML、CSS、内联 SVG 和终端仿真界面，不使用真实软件截图。

本册不是 Docker 官方手册的中文缩写版。每章都必须同时回答：

- 现在要做什么；
- 为什么这样做；
- 成功后是什么样；
- 失败时先看什么；
- 这一步会不会影响现有服务或已有数据。

## 1. 第三册目标读者

### 核心读者

- 已经完成第一册，拥有一台可以通过 SSH 登录的 Ubuntu VPS；
- 听说过 Docker，但不知道它解决什么问题；
- 希望以后部署 Open WebUI、Dify、n8n、Supabase 等服务；
- 可以复制命令，但无法判断命令会创建、停止还是删除什么；
- 不理解镜像、容器、仓库、标签、端口、卷和 Compose；
- 可能已经完成第二册，并在同一台服务器上运行 3X-UI / Xray；
- 希望部署服务，但不准备先系统学习 Linux 运维或网络工程。

### 默认具备的能力

- 能根据第一册交接卡找到服务器 IP、管理员用户名和登录凭证；
- 能在 Windows 或 macOS 上打开终端并使用 SSH 登录；
- 会复制、粘贴命令，并能区分命令与命令输出；
- 会使用 `exit` 退出服务器；
- 知道公网 IPv4、端口和防火墙是不同概念，但不要求熟练配置；
- 愿意在执行删除命令前停下来核对对象名称和备份状态。

### 默认不具备的知识

- 不理解容器与虚拟机、普通进程之间的区别；
- 不知道镜像是模板，容器是由镜像创建的运行实例；
- 不知道镜像标签可能变化，也不知道镜像来源需要判断；
- 不知道 `8080:80` 两个数字分别属于主机和容器；
- 不知道容器被删除后，容器可写层中的数据可能一起消失；
- 不知道 named volume 与 bind mount 的管理边界；
- 不知道 YAML 缩进、Compose 项目和 service 是什么；
- 不知道 `docker compose down`、`down -v` 和 `system prune` 的影响不同；
- 不知道 Docker 发布端口与 UFW 之间存在需要单独核验的关系；
- 不知道加入 `docker` 用户组会获得接近 root 的权限；
- 不会使用 `ps`、`logs`、`inspect` 和 `exec` 判断故障位置。

### 需要主动消除的焦虑

- 害怕 Docker 会替换或破坏现有 Ubuntu 系统；
- 害怕安装 Docker 后原有 3X-UI / Xray 立即停止；
- 看到大量镜像层下载信息时不知道是否失败；
- 不知道容器显示 `Exited` 是正常结束还是故障；
- 不知道浏览器打不开时应该查容器、端口、防火墙还是网络；
- 担心修改 Compose 文件后丢失原有数据；
- 不知道哪些目录应该备份，哪些镜像可以重新下载；
- 不敢执行清理命令，或相反，误以为所有 `prune` 都是无风险清理；
- 不理解“容器隔离”并不等于“容器内的程序绝对安全”。

## 2. 阅读前提

读者开始前需要：

- 一台正在运行、可以通过 SSH 登录的 Ubuntu 24.04 LTS VPS；
- x86_64 / amd64 CPU 架构；
- 一个 `root` 账户，或一个已经验证可以使用 `sudo` 的管理员账户；
- 至少一个独立公网 IPv4；
- 稳定的服务器网络连接，能够访问 Docker 官方软件源和镜像仓库；
- 至少约 2 GB 可用磁盘空间，用于安装、镜像和练习数据；
- 一份第一册交接卡，至少记录 IP、地区、系统、管理员用户名和凭证位置；
- 如果已经完成第二册，能够找到 3X-UI 面板端口、VLESS 入站端口等现有端口记录；
- 能够遵守所在地法律、镜像许可、软件条款和组织安全制度。

读者不需要提前具备：

- Docker Desktop；
- 域名、DNS、HTTPS 或 Cloudflare 账户；
- Docker Hub 账户；
- Git 或 GitHub 账户；
- 编程语言、Dockerfile 或应用开发知识；
- Kubernetes、Swarm 或集群运维知识；
- GPU 或 NVIDIA 驱动；
- 一台全新的空白服务器。

### 关于共用现有服务器

本书可以在第一册交付的服务器上学习。如果该服务器已经运行第二册的 3X-UI / Xray，
正文必须先带读者完成“现有服务与端口清点”，并满足以下边界：

- 不停止、不删除、不重装 3X-UI / Xray；
- 不占用已有端口；
- 不修改第二册的入站配置；
- 不把 `/root`、`/etc` 或现有应用目录整体挂载进练习容器；
- 不执行无法解释影响范围的批量清理命令；
- 资源明显不足时，建议使用另一台练习服务器，而不是在生产用途服务器上硬做实验。

## 3. 学习结果

### 认知结果

完成第三册后，读者应当能够：

- 用自己的话解释 Docker 容器是主机上的隔离进程，而不是一台完整虚拟机；
- 区分 registry、repository、image、tag、container 和 service；
- 理解镜像通常是只读分层模板，容器还拥有自己的可写层；
- 理解停止容器、删除容器、删除镜像和删除 volume 是四种不同操作；
- 看懂 `主机地址:主机端口:容器端口` 的关系；
- 理解“容器内已监听”不等于“公网可以访问”；
- 区分 named volume、bind mount 和容器可写层；
- 理解 Compose 文件描述期望状态，不是正在运行的容器本身；
- 知道环境变量不应被默认当作安全的秘密存储；
- 知道镜像更新、容器重建、数据迁移和应用升级不是同一个动作；
- 知道容器隔离不能替代主机安全、应用鉴权、备份和最小权限。

### 操作结果

完成第三册后，读者必须已经能够：

| 交付物或能力 | 验收证据 |
| --- | --- |
| Docker Engine 已安装 | `sudo docker version` 能显示客户端和服务器信息 |
| Compose plugin 已安装 | `sudo docker compose version` 能显示插件版本信息 |
| 首个容器运行成功 | `hello-world` 输出成功说明，读者能解释它为什么会自动结束 |
| 能管理容器生命周期 | 能查看运行中和已停止容器，并能对指定练习容器执行启动、停止和删除 |
| 能判断端口关系 | 能指出主机端口、容器端口、监听地址和公网入口 |
| 能安全验证 Web 服务 | 先通过服务器本机访问，再按章节说明决定是否开放公网 |
| 能保存持久数据 | 能分别完成一次 named volume 和 bind mount 验证 |
| 拥有一个 Compose 项目 | 固定目录中存在可读的 `compose.yaml` 和必要的示例配置 |
| 能重复部署 | `docker compose up -d` 后服务状态与预期一致 |
| 能停止而不误删数据 | 能解释 `stop`、`down` 与 `down -v` 的差异 |
| 能做基础排错 | 会使用 `ps`、`logs`、`inspect`、端口检查和磁盘检查定位问题 |
| 能维护服务 | 已完成一次受控更新演练和一次可验证的配置或数据备份 |
| 能进入后续图书 | 能把 Compose 项目目录、端口、数据、版本和备份位置写入交接卡 |

### 整册完成条件

建议只把第 1—12 章计入完成率。以下内容不计入：

- “开始之前”；
- 附录；
- 资料来源。

12 章全部完成时可以显示整册完成，但最后一章的完成清单必须核验：

- Docker Engine 与 Compose 均可用；
- 练习 Compose 项目可以重新创建；
- 读者知道项目使用的端口；
- 读者知道数据和配置分别保存在哪里；
- 读者至少完成一次备份并验证备份文件存在；
- 交接卡不包含真实密码、私钥、令牌或其他敏感正文。

“容器正在运行”不等于完成第三册。“浏览器打开了页面”也不等于已经掌握数据和维护。

## 4. 不包含的内容

第三册不负责：

- 购买 VPS 或处理支付、实名和账户审核；
- 从零教授 SSH；登录失败应返回第一册对应章节；
- 安装或配置 3X-UI、Xray、VLESS、Reality 或客户端；
- 购买域名、配置 DNS、HTTPS、证书、Cloudflare 或反向代理；
- 系统教授 Linux 文件权限、Shell 编程、systemd 或 iptables；
- 使用 Docker Desktop 作为服务器主线；
- 深入编写 Dockerfile、多阶段构建、BuildKit 或私有构建流水线；
- 配置 Docker Hub 私有仓库、企业 Registry 或镜像签名体系；
- Kubernetes、Docker Swarm、Nomad 或多服务器集群；
- GPU 容器、NVIDIA Container Toolkit 或 AI 模型存储优化；
- Portainer、Watchtower 等第三方管理与自动更新工具；
- rootless Docker 的完整部署；
- macvlan、ipvlan、overlay 等高级网络；
- 自动备份、异地容灾或生产级数据库恢复体系；
- 为具体业务应用制定容量、监控、告警和高可用方案；
- 推荐来源不明的镜像加速器、安装脚本或第三方二进制包。

本书可以解释 Dockerfile、Registry、healthcheck、secrets 和 rootless 等词的边界，但不把
它们扩展成独立高级教程。

### 章节学习路径

全书分为四个连续部分，不允许读者跳过关键概念后直接复制 Compose 文件。

| 部分 | 章节 | 阶段交付 |
| --- | --- | --- |
| 建立对象模型 | 第 1—2 章 | 能区分 Engine、镜像、容器、仓库和标签 |
| 安装与运行 | 第 3—5 章 | Docker 与 Compose 可用，能管理一个容器的生命周期 |
| 连接、数据与配置 | 第 6—8 章 | 能判断端口暴露范围，能保存数据并保护敏感配置 |
| 项目化与维护 | 第 9—12 章 | 拥有可重复部署、可排错、可备份和可交接的 Compose 项目 |

第 3、6、7、9、11 章是操作风险和理解难度较高的核心章：

- 第 3 章不能只给安装命令，必须逐组解释软件源、软件包和验证结果；
- 第 6 章必须把端口、监听地址、防火墙和公网访问画成一条完整链路；
- 第 7 章必须通过“删除并重建练习容器”实际证明数据是否持久；
- 第 9 章是全书的综合样板章，需要让非程序员也能直接维护 `compose.yaml`；
- 第 11 章不得把清理命令写成无条件建议，必须先建立备份和回退点。

- 从第一册交接卡确认系统、架构、磁盘、管理员权限和登录方式；
- 如果已经完成第二册，记录当前服务、监听端口和用途；
- 明确所有练习对象使用统一前缀，避免误操作已有容器或目录；
- 说明 Docker 安装会创建服务、网络接口和防火墙规则；
- 成功状态：读者确认服务器符合主线环境，并保存一份练习前清点表；
- 失败判断：系统或架构不符、磁盘过少、无 sudo 权限、现有业务无法辨认，或服务器
  已处于异常状态。

### 第 1 章：Docker 到底解决什么问题？

- 用“应用需要的文件、运行环境和启动方式”解释容器的价值；
- 对比容器、虚拟机和直接安装，不宣传容器是所有场景的唯一答案；
- 解释容器是隔离进程，通常共享主机内核；
- 解释 Docker Engine、Docker CLI 和 daemon 的基本关系；
- 说明容器隔离不等于绝对安全；
- 成功状态：读者能够判断“镜像”和“正在运行的容器”不是同一对象；
- 失败判断：读者仍把每个容器理解为一台拥有独立内核的 VPS。

### 第 2 章：镜像、容器、仓库和标签是什么？

- 解释 registry、repository、image、tag、digest 和 container 的关系；
- 说明镜像分层与不可变的基本含义，不深入存储驱动；
- 说明标签是可读引用，但标签指向的内容可能更新；
- 教读者识别 Docker Official Image、发布者和架构支持；
- 说明不要运行来源不明、要求 `--privileged` 或挂载 Docker socket 的镜像；
- 成功状态：读者能从一个示例镜像名中指出仓库和标签；
- 失败判断：读者认为删除容器会自动删除镜像，或认为相同标签永远代表相同内容。

### 第 3 章：从官方软件源安装 Docker Engine

- 检查 Ubuntu 版本、CPU 架构和已有冲突包；
- 按 Docker 官方 APT 软件源流程安装 Engine、CLI、containerd、Buildx 和 Compose plugin；
- 解释每组命令正在增加什么软件源或安装什么包；
- 使用 `docker version`、`docker compose version` 和服务状态完成验证；
- 使用 `hello-world` 验证端到端链路；
- 解释为什么正文默认保留 `sudo`；
- 说明便捷安装脚本不作为生产主线；
- 成功状态：客户端与服务器版本可见，Compose plugin 可用，`hello-world` 正常结束；
- 失败判断：软件源签名、包冲突、daemon 未启动、权限不足、DNS 或镜像拉取失败。

### 第 4 章：运行第一个容器，看懂 `docker run`

- 把 `docker run` 拆解为拉取镜像、创建容器、启动进程、连接输出；
- 使用 `--name` 给练习容器稳定命名；
- 解释前台、后台、`--rm` 和容器主进程退出；
- 展示镜像不存在于本地时的拉取过程；
- 让读者能够在命令、镜像、容器和输出之间建立关系；
- 成功状态：读者能运行指定练习容器，并在 `docker ps -a` 中找到它；
- 失败判断：镜像名错误、架构不兼容、拉取超时或容器立即异常退出。

### 第 5 章：启动、停止和删除：容器的生命周期

- 区分 create、start、running、stopped、remove；
- 介绍 `docker ps` 与 `docker ps -a`；
- 使用明确名称执行 `start`、`stop`、`restart`、`rm`；
- 解释停止容器不会删除它，删除容器不会自动删除镜像和 named volume；
- 介绍 restart policy 的目的和默认行为；
- 所有删除操作先展示对象和影响范围；
- 成功状态：读者能重启练习容器并确认状态变化；
- 失败判断：名称选错、端口仍被占用、主进程持续退出或误把镜像当容器。

### 第 6 章：端口映射：容器怎样被访问？

- 用流程图解释浏览器、服务器公网 IP、主机端口、Docker 转发和容器端口；
- 分别解释 `127.0.0.1:8080:80` 与 `8080:80`；
- 先使用 `curl` 在服务器本机验证，再决定是否向公网发布；
- 解释 `EXPOSE` 不等于发布端口；
- 解释云防火墙、主机防火墙和 Docker 发布规则属于不同层；
- 明确 Docker 发布端口可能绕过读者对 UFW 的直觉预期；
- 检查与 3X-UI / Xray 等既有服务的端口冲突；
- 成功状态：本机访问成功，读者能指出实际监听地址和访问路径；
- 失败判断：容器未监听、主机端口冲突、绑定地址错误、防火墙未开放或公网入口错误。

### 第 7 章：数据放在哪里：volume 与目录映射

- 解释容器可写层为什么不适合作为唯一持久数据位置；
- 使用一个可观察文件验证 named volume 在容器删除后仍然存在；
- 使用 bind mount 把可编辑配置或静态文件映射进容器；
- 解释主机路径、容器路径、只读挂载和文件所有权；
- 说明 bind mount 默认可写，可能修改或删除主机文件；
- 说明 volume 的生命周期独立于容器，清理时必须单独核对；
- 成功状态：读者能重建容器并确认数据仍然存在；
- 失败判断：路径写错、文件权限不符、挂载遮盖容器原有文件或误删 volume。

### 第 8 章：配置、环境变量与敏感信息

- 区分普通配置、环境变量、密码、API key、证书和私钥；
- 解释 Compose 中 `environment`、变量替换和 `env_file` 的作用边界；
- 明确 `.env` 只是配置载体，不是自动加密的秘密保险箱；
- 说明敏感值不能写入公开仓库、截图、命令历史或普通笔记；
- 介绍 Compose secrets 的文件挂载模型和“镜像必须支持”这一前提；
- 建立 `.env.example` 与真实本地配置分离的维护习惯；
- 成功状态：读者能识别哪些值可以公开，哪些值只能记录存放位置；
- 失败判断：敏感值进入 Compose 文件、Git、终端截图或容器日志。

### 第 9 章：用 Compose 管理一套服务

- 解释 Compose project、service、image、ports、volumes 和 restart；
- 从上一章的 `docker run` 命令转换成可读的 `compose.yaml`；
- 教读者识别 YAML 缩进，避免用复杂嵌套参数增加维护难度；
- 使用 `docker compose config` 在启动前检查解析结果；
- 使用 `up -d`、`ps`、`logs`、`stop`、`start` 和 `down`；
- 说明 Compose 默认网络和服务名通信，但不展开高级网络驱动；
- 解释修改 Compose 文件后为何需要重建容器；
- 成功状态：读者能从空状态重复创建同一套练习服务；
- 失败判断：YAML 缩进错误、变量缺失、端口冲突、镜像拉取失败或服务持续重启。

### 第 10 章：看状态、读日志、定位常见故障

- 建立“主机 → Docker daemon → 镜像 → 容器进程 → 端口 → 防火墙 → 浏览器”的排查顺序；
- 使用 `docker compose ps`、`docker compose logs`、`docker inspect` 和受控的 `exec`；
- 区分 `Created`、`Running`、`Exited`、`Restarting` 和可能的健康状态；
- 解释错误码、时间戳和最近日志，不要求读者读懂所有应用日志；
- 覆盖磁盘不足、端口占用、权限问题、变量缺失、架构不符和网络失败；
- 说明何时停止尝试并恢复到最后已知正常状态；
- 成功状态：读者能把故障定位到至少一个明确层级；
- 失败判断：只反复执行 `restart`，或在未备份时删除 volume 和项目目录。

### 第 11 章：更新、备份、恢复与安全清理

- 解释拉取镜像、重建容器、应用迁移和数据迁移的区别；
- 更新前记录当前镜像引用、Compose 文件和备份位置；
- 对配置、bind mount 和 named volume 分别制定备份方法；
- 完成一次小范围恢复验证，而不是只确认压缩包存在；
- 解释日志增长、镜像缓存和磁盘占用；
- 分别说明 image、container、network、volume 和 system prune；
- 将 `down -v`、`volume prune`、`system prune --volumes` 标为高风险操作；
- 成功状态：读者完成更新演练，服务可用，数据仍在，且能够找到备份；
- 失败判断：使用浮动标签后无法确认旧版本、备份未验证、磁盘继续增长或清理范围不明。

### 第 12 章：整理 Compose 项目，进入下一册

- 整理统一的项目目录和可公开配置；
- 记录镜像、标签或摘要、端口、监听地址、数据路径、环境文件位置和备份位置；
- 检查服务重启后是否恢复；
- 检查是否遗留不再使用的公网端口；
- 说明第四册怎样接入域名、DNS、HTTPS 与反向代理；
- 说明第五册以后怎样复用 Compose 项目结构；
- 说明不要把真实秘密写入交接卡；
- 成功状态：另一位维护者能根据交接卡找到项目并完成只读检查；
- 失败判断：只有一条历史命令，没有 Compose 文件、数据说明、端口说明或回退信息。

## 11. 技术事实校订清单

所有安装命令、软件支持范围、示例镜像和外部事实必须标注校订日期，并优先引用 Docker
官方文档。正文不能依赖 `latest` 标签长期保持相同行为。

### 已核验的主线依据

截至 2026-07-28，策划阶段已从 Docker 官方文档确认：

- Docker Engine 的 Ubuntu 安装文档包含 Ubuntu 24.04 LTS amd64 支持；
- 官方 APT 软件源安装包含 `docker-ce`、`docker-ce-cli`、`containerd.io`、
  `docker-buildx-plugin` 和 `docker-compose-plugin`；
- 官方安装页以 `docker run hello-world` 验证；本书增加 `--rm`，避免遗留随机名称的临时容器；
- 便捷安装脚本主要面向测试和开发，不应作为生产主线；
- 当前 Compose plugin 使用 `docker compose` 子命令；插件版本号不以 `v2` 作为固定成功条件；
- 未指定主机地址的端口发布默认可能绑定所有主机地址；
- Docker 发布端口与 UFW / firewalld 的关系需要单独理解，不能只看 UFW 状态；
- named volume 的生命周期独立于容器，删除容器不会自动删除 volume；
- bind mount 默认可写，容器可能修改或删除主机文件；
- `docker` 用户组授予接近 root 的权限；
- Docker 默认不会自动清理所有未使用对象，volume 也不会因为容器停止而自动删除；
- `docker system prune --volumes` 会把未使用 volume 纳入清理范围；
- Compose secrets 以文件形式挂载到 `/run/secrets/<secret_name>`，且服务需显式声明；
- Docker 官方建议不要用环境变量传递密码等敏感信息。

## 12. 内容风险清单

| 风险 | 严重度 | 可能后果 | 策划阶段控制方式 |
| --- | --- | --- | --- |
| 把端口直接绑定到全部主机地址 | 高 | 未鉴权练习服务暴露到公网 | 默认先绑定 `127.0.0.1`，公网演示单独成步骤 |
| 只看 UFW 判断 Docker 端口是否暴露 | 高 | 实际开放范围与读者判断不一致 | 单列 Docker 防火墙限制并做实际监听检查 |
| 把用户加入 `docker` 组却不解释权限 | 高 | 普通账户获得接近 root 的控制能力 | 主线保留 `sudo docker`，用户组仅作安全边界说明 |
| 使用 `down -v` 或 volume prune | 高 | 永久删除持久数据 | 不作为常规清理命令，执行前要求备份与对象核对 |
| 运行来源不明的镜像 | 高 | 主机、凭证或数据受损 | 主线只用官方镜像，教读者核对发布者和参数 |
| 使用 `--privileged` 或挂载 Docker socket | 高 | 容器可能控制主机或 Docker daemon | 主线禁止，遇到此要求时提示停止并查官方文档 |
| 在 YAML、`.env` 或截图中公开秘密 | 高 | 密码、API key 或令牌泄露 | 建立信息分级和示例占位值，交接卡只记录路径 |
| 与第二册端口或服务冲突 | 高 | 现有网络节点中断 | 开始前清点监听端口，不修改已有服务 |
| bind mount 路径或权限写错 | 中高 | 容器覆盖主机文件或无法启动 | 使用专用练习目录，先只读或备份，再开放写入 |
| 把容器删除当作应用卸载 | 中高 | 配置和数据边界不清，产生残留或丢失 | 分对象讲生命周期，删除前显示关联对象 |
| 浮动镜像标签发生变化 | 中高 | 重新部署结果不同或升级失败 | RC 固定并记录验证标签，重要场景记录摘要 |
| 服务器磁盘被镜像和日志占满 | 中高 | Docker 与现有服务同时异常 | 教磁盘检查、日志边界和分类清理 |
| 中国用户拉取软件或镜像失败 | 中 | 安装或启动中断 | 从服务器端分层诊断 DNS、网络、仓库；不推荐未知镜像源 |
| amd64 / arm64 镜像不匹配 | 中 | 容器无法启动或行为异常 | 主线固定 amd64，镜像页校验架构 |
| 把 `.env` 当成加密保险箱 | 中 | 敏感数据被复制、备份或提交 | 明确 `.env` 是普通文件，介绍 secrets 边界 |
| 自动更新破坏数据兼容性 | 中 | 新版本无法启动或数据迁移失败 | 不引入自动更新；先备份、记录版本、受控重建 |
| 日志只展示应用报错，读者误判系统原因 | 中 | 反复重启而不定位故障 | 使用分层排查树并限制每一步的结论 |
| 内容演变成命令速查表 | 中 | 读者会复制但无法判断影响 | 每个操作都包含对象、原因、成功和失败状态 |
| 示例过于简单，无法迁移到后续应用 | 中 | 学完仍看不懂 Compose 项目 | 贯穿端口、配置、数据、日志、更新和交接 |
| 示例过于复杂 | 中 | YAML 和多服务关系压垮零基础读者 | 主线保持单服务，多服务只解释概念或留给应用册 |
| 与第四册边界重复 | 低中 | 域名、HTTPS 和反向代理内容重复维护 | 第三册只交付监听端口和服务状态 |
| 官方界面或输出变化 | 低中 | 仿真界面与当前版本不一致 | 不声称像素级截图，RC 前重新校订 |
