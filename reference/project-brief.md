# Project Brief

## 项目名称

《AI 基础设施从零开始》

英文工作名：

AI Infrastructure Books

## 当前项目

第二册：

《拥有自己的海外网络：从 VPS 到 Clash，只需要 30 分钟》

## 项目背景

越来越多普通用户开始使用 ChatGPT、Claude、Dify、Open WebUI、n8n、Supabase 和各类 AI 开发工具。

但当他们进一步尝试：

- 部署 AI 工具
- 使用海外服务
- 建立自己的服务器
- 配置数据库
- 管理域名
- 使用 Docker
- 搭建自动化流程

就会进入传统技术文档的世界。

现有技术教程通常存在以下问题：

1. 默认读者懂 Linux。
2. 默认读者懂命令行。
3. 只告诉用户复制什么命令，不解释为什么。
4. 软件版本变化后，截图迅速失效。
5. 出错时缺少判断路径。
6. 教程之间互相割裂，没有形成能力体系。
7. 对安全、隐私和维护成本解释不足。

本项目希望填补这一空白。

## 项目愿景

建立一套中文互联网中高质量、可持续维护的 AI 基础设施入门图书。

它需要帮助普通用户从：

> “我完全不懂服务器。”

逐步走到：

> “我知道系统由哪些部分组成，也知道出现问题时应该检查哪里。”

项目不以培养专业运维工程师为目标。

项目的核心目标是帮助普通用户建立：

- 基础认知
- 操作能力
- 判断能力
- 排错能力
- 安全意识

## 当前第二册的目标

第二册需要帮助用户从一台已经购买的 Ubuntu VPS 出发，完成以下过程：

```text
登录 VPS
→
安装 3X-UI
→
理解 Xray、入站与协议
→
创建 VLESS Reality 节点
→
生成订阅
→
导入 Clash Verge Rev
→
导入 Shadowrocket
→
验证出口 IP 与连接状态
→
建立基础维护能力
```

完成第二册后，用户不需要成为网络工程师，但应当知道：

- VPS 是什么
- SSH 是什么
- Terminal 是什么
- 3X-UI 与 Xray 的关系
- 入站与出站的区别
- VLESS、Reality、Vision、UUID 分别是什么
- 订阅链接有什么作用
- Clash 与 Shadowrocket 扮演什么角色
- 如何判断服务器、面板、节点或客户端哪里出了问题
- 自建服务为什么不等于绝对匿名
- 哪些信息不能公开

## 目标用户

### 核心用户

- AI 工具重度用户
- 内容创作者
- 知识工作者
- 跨境从业者
- 独立开发者中的非技术型用户
- OPC 经营者
- 小企业主

### 用户能力假设

默认用户：

- 会使用浏览器
- 会安装普通桌面软件
- 会复制和粘贴
- 能理解账号、密码和网址

默认用户不会：

- Linux
- Shell
- SSH
- 网络协议
- 防火墙
- DNS
- Git
- 前端开发
- JSON 配置

## 用户的核心焦虑

用户在操作过程中最常见的心理状态包括：

- 害怕输错命令
- 害怕把服务器弄坏
- 不知道密码是否已经输入
- 不知道页面打不开是自己错了还是服务器错了
- 不理解为什么要填写某个字段
- 不知道成功状态应该是什么样
- 不敢修改配置
- 不知道是否需要配置出站
- 不知道端口冲突意味着什么
- 不知道订阅和节点是什么关系

内容和界面必须主动消除这些焦虑。

## 核心产品原则

### 1. 先建立地图，再开始操作

每一册需要先向读者展示完整工作链路。

不能一开始就让用户复制命令。

### 2. 每一页回答一个问题

页面和章节应该围绕用户问题组织，而不是围绕软件菜单组织。

例如：

不应只写：

> SSH 登录

更适合写：

> 我怎样进入刚刚购买的服务器？

### 3. 解释为什么

每个关键操作都需要解释：

- 为什么需要这样做
- 为什么选择这个方案
- 是否存在其他方案
- 什么情况下不适用

### 4. 显示成功状态

读者必须能够看到：

- 成功后的终端是什么样
- 成功后的面板是什么样
- 成功后的客户端是什么样
- 错误提示意味着什么

### 5. 错误是正文的一部分

故障排查不能只放在书尾。

关键步骤附近应直接提示：

- 常见错误
- 判断方式
- 修复方式
- 不应该做什么

### 6. 不依赖真实截图

真实截图更新成本高，且容易因为版本、系统和语言不同而失效。

本项目采用：

- HTML
- CSS
- 内联 SVG
- 仿真终端
- 仿真浏览器
- 仿真软件面板

仿真界面主要呈现：

- 信息结构
- 字段关系
- 操作顺序
- 成功状态

不追求对某一软件版本进行像素级复刻。

### 7. 手机优先

很多读者会：

- 在手机上看教程
- 在电脑上操作
- 在手机和电脑之间来回切换

因此手机端不是桌面版的缩小版本，而是一级阅读场景。

## 写作风格

整体风格应当：

- 准确
- 克制
- 耐心
- 不卖弄
- 不制造神秘感
- 不羞辱新手
- 不故意使用复杂术语

避免：

- “很简单”
- “显然”
- “自行配置”
- “这里不再赘述”
- “懂的都懂”
- “一键解决所有问题”

允许使用生活化比喻，但比喻之后必须回到准确概念。

例如：

> SSH 像没有图形界面的远程桌面。

之后仍需要解释 SSH 是加密远程登录协议。

## 当前技术方案

第二册当前采用：

- Ubuntu VPS
- SSH
- 3X-UI
- Xray-core
- VLESS
- TCP / RAW
- Reality
- xtls-rprx-vision
- Clash Verge Rev
- Shadowrocket

在没有明确产品决策的情况下，不应擅自替换为其他方案。

如未来技术环境发生变化，应先：

1. 核查官方维护状态。
2. 分析迁移成本。
3. 提出替换方案。
4. 等待确认。
5. 再修改全书。

当前完整 HTML 原型：

```text
source/book02-v1.html
```

它包含：

- 12 个章节
- 附录
- 故障排查
- 术语表
- 仿真终端
- 仿真 3X-UI
- 仿真 Clash
- 仿真 Shadowrocket
- 深色模式
- 代码复制
- 阅读进度
- 搜索
- 打印样式

正式项目需要将该文件拆分为：

- 内容文件
- 页面布局
- 可复用组件
- 设计 Token
- 交互脚本

但不得在迁移过程中遗漏正文。

- 设计系统
- 组件系统
- 内容规范
- 术语规范
- 发布流程

## 产品形态

项目未来可能同时输出：

- 在线文档网站
- 单文件离线 HTML
- PDF
- 适合手机阅读的长图文
- 纸质书或电子书
- 配套检查表

因此架构不应与单一部署平台强绑定。

## 技术架构偏好

优先考虑：

- Astro
- TypeScript
- 静态站点生成
- Markdown 或 MDX
- CSS Variables
- 少量原生 JavaScript
- 可复用组件
- 无后端依赖

需要避免：

- 不必要的客户端 JavaScript
- 重型状态管理
- 过度工程化
- 大量第三方 UI 库
- 依赖远程字体和图片
- 必须联网才能阅读正文
- 与单一云平台深度绑定

## 非目标

当前阶段不做：

- 用户注册
- 评论系统
- 在线支付
- 会员系统
- 云端学习记录
- 社区
- 在线服务器管理
- 自动替用户创建 VPS
- 自动替用户部署节点
- 第三册正文开发
- 大规模内容改写

## 当前阶段的成功标准

第一阶段完成时，应当满足：

1. 正式项目可以本地运行。
2. 第二册全部内容已经迁移。
3. 原型文件仍然保留。
4. 章节可以独立访问。
5. 手机、平板和桌面可读。
6. 深色模式完整可用。
7. 目录、搜索、复制和阅读进度可用。
8. 刷新后仍保留章节完成状态。
9. 打印与 PDF 导出可读。
10. 项目能够完成 production build。
11. 没有明显内部链接错误。
12. 后续可以继续增加第一册和第三册。
13. 正文不依赖 JavaScript 才能阅读。
14. 项目结构和运行方式有文档说明。

## 决策权限

项目 Owner 负责决定：

- 书名
- 章节结构
- 技术路线
- 内容增删
- 产品定位
- 发布方式

Codex 可以：

- 提出建议
- 分析风险
- 建立代码
- 重构组件
- 修复错误
- 补充测试和文档

Codex 不应未经确认：

- 改变书名
- 删除章节
- 替换核心技术方案
- 大规模改写正文
- 开始开发其他册
- 引入收费服务
- 引入重型框架
- 添加用户系统
