<section className="book-section" id="ch8-result">
  ## 这一章要解决什么

  容器启动以后，应用仍然需要知道怎样运行，例如：

  - 使用开发模式还是正式模式；
  - 页面显示什么语言；
  - 日志输出到什么级别；
  - 数据库地址在哪里；
  - 应用从哪里读取令牌或密码。

  这些值都可以被笼统称为“配置”，但风险完全不同。把颜色主题写进公开文件通常问题不大，把 root 密码、SSH 私钥或 API key 写进同一个文件则可能造成严重泄露。

  本章先建立四类信息：

  <ComparisonTable>

  | 类型 | 教学示例 | 是否可以进入公开模板 | 主要风险 |
  | --- | --- | --- | --- |
  | 普通配置 | 语言、时区、显示颜色、日志级别 | 通常可以 | 写错会改变行为 |
  | 连接配置 | 主机名、端口、数据库名 | 视环境而定 | 暴露内部结构或连接位置 |
  | 敏感凭证 | 密码、API key、访问令牌、私钥 | 不可以 | 他人可冒用身份或访问数据 |
  | 恢复凭证 | 2FA 恢复码、备份密钥、主密钥 | 绝不进入项目 | 泄露后可能失去最终控制权 |

  </ComparisonTable>

  <Callout type="danger" title="本章不会要求你粘贴任何真实秘密">
    所有文件和命令只使用 `practice`、`blue`、`replace-with-...` 等明显示例值。不要把真实密码、令牌、私钥或订阅地址替换进去再截图、提交或发给他人。
  </Callout>
</section>

<section className="book-section" id="ch8-env-file">
  ## 第二步：用 env file 保存普通配置

  env 是 environment（环境）的缩写。environment variable（环境变量）是一组由运行环境提供给进程的名称和值。

  打开普通配置文件：

  <CodeBlock
    label="打开 public.env"
    code="nano public.env"
  />

  粘贴：

  <CodeBlock
    label="public.env"
    code={publicEnvFile}
  />

  保存并退出，然后限制文件权限：

  <CodeBlock
    label="限制并检查 public.env"
    code={"chmod 600 public.env\nls -l public.env\nsed -n '1,20p' public.env"}
  />

  `600` 表示所有者可以读写，其他账户没有权限。当前文件只有普通教学配置，但从一开始养成限制配置文件权限的习惯，可以减少后续误用。

  成功状态：

  - 权限字符串通常以 `-rw-------` 开头；
  - 文件只有两行教学值；
  - 没有引号、冒号或多余空格；
  - 没有密码、IP、令牌或私钥。

  <Callout type="warning" title="env file 是普通文本文件">
    文件名以 `.env` 结尾、权限是 600、目录名叫 secrets，都不会自动加密内容。拥有相应主机权限的人仍可读取它。
  </Callout>
</section>

  3. 在容器内打印这两个值；
  4. 命令结束后通过 `--rm` 删除临时容器；

    BOOK03_MODE=practice<br />
    BOOK03_COLOR=blue
  </TerminalMock>

  失败判断：

  - `no such file or directory`：当前路径或 `public.env` 不正确；

<section className="book-section" id="ch8-dotenv">
  ## `.env`、`env_file` 和容器环境不是一回事

  这三个名字经常在教程中混用：

  <ComparisonTable>

  | 名称 | 主要作用 | 是否自动进入容器 |
  | --- | --- | --- |
  | 任意 env file | 供 `docker run --env-file` 或 Compose `env_file` 读取 | 只有明确引用时才进入 |
  | Compose 项目中的 `.env` | 常用于 Compose 变量插值 | 不保证自动注入 service |
  | `environment` | Compose service 的容器环境配置 | 会进入对应容器 |
  | Compose `env_file` | 从指定文件向 service 提供环境变量 | 会进入对应容器 |

  </ComparisonTable>

  interpolation（插值）表示 Compose 在解析配置时，把 `${NAME}` 替换成某个值。插值发生在 Compose 配置层；应用进程是否得到这个变量，还取决于 service 的 `environment` 或 `env_file` 等配置。

  <Callout type="info" title="第 9 章先不加入 env file">
    下一章的 Nginx 静态页面不需要环境变量。Compose 样章会先验证端口、bind mount 和重启策略，避免把不必要配置堆进第一份 `compose.yaml`。
  </Callout>
</section>

<section className="book-section" id="ch8-config-file">
  ## 什么内容更适合配置文件

  当配置具有层级、注释或多行结构时，配置文件通常比大量环境变量更容易审阅。例如：

  - 应用功能开关；
  - 日志格式和级别；
  - 非敏感的服务地址；
  - Web 服务器路由；
  - 工作流或任务定义。

  使用 bind mount 提供配置时，继续遵守第 7 章边界：

  - source 是专用项目目录中的具体文件或小目录；
  - 不把 `/etc` 或整个用户家目录挂进去；
  - 应用只需读取时使用 `readonly`；
  - 修改前备份已知可用版本；
  - 修改后先做配置验证，再重建或重载服务。

  <Callout type="warning" title="只读挂载只限制容器写回，不隐藏内容">
    `readonly` 可以阻止容器通过该挂载修改主机文件，但容器仍然能够读取文件。不要把不需要某个 service 的秘密挂给它。
  </Callout>
</section>

<section className="book-section" id="ch8-secret">
  ## 敏感信息应该怎样思考

  secret（秘密或敏感凭证）是泄露后可以授予访问能力、冒用身份或削弱恢复能力的数据，例如：

  - root 或管理员密码；
  - SSH 私钥；
  - 云平台 API key；
  - 数据库密码；
  - 第三方服务访问令牌；
  - 2FA 恢复码；
  - Reality 私钥、UUID 和订阅 URL；
  - 加密备份的解密密钥。

  Docker Compose 支持把 secret 授予明确的 service。被授予的容器通常在 `/run/secrets/<secret_name>` 以文件方式读取它。

  下面只展示结构，使用不存在的示例域名镜像，不能直接运行：

  <CodeBlock
    label="Compose secret 结构示例（不要运行）"
    code={composeSecretExample}
  />

  关系是：

  <FlowDiagram>
    <div className="flow-node">
      <strong>主机 secret 文件</strong>
      <small>不提交、不公开、限制权限</small>
    </div>
    <div className="flow-node">
      <strong>top-level secrets</strong>
      <small>声明 secret 来源</small>
    </div>
    <div className="flow-node">
      <strong>service 授权</strong>
      <small>只有需要的 service 引用</small>
    </div>
    <div className="flow-node">
      <strong>/run/secrets/...</strong>
      <small>应用按文件读取</small>
    </div>
  </FlowDiagram>

  <Callout type="warning" title="Compose secrets 不是自动托管的云密码库">
    在本机 Compose 场景中，secret 仍然来源于主机文件或环境。它可以减少把值直接放进容器环境的风险，并按 service 授权，但不会自动加密主机源文件，也不会替你完成轮换、审计和异地保护。
  </Callout>

  还要确认应用是否支持“从文件读取”。一些镜像使用形如 `PASSWORD_FILE` 的约定，但这不是所有镜像自动具备的 Docker 魔法；必须查看该镜像的官方文档。
</section>

<section className="book-section" id="ch8-review">
  ## 写入配置前的六问

  每次准备写入值时，先问：

  1. 这个值泄露后，别人能获得什么能力；
  2. 应用是否真的需要它；
  3. 只有一个 service 需要，还是多个 service 都需要；
  4. 能否使用权限更小、有效期更短的凭证；
  5. 它会不会出现在命令历史、inspect、日志、截图或备份中；
  6. 泄露后在哪里撤销或轮换。

  <ComparisonTable>

  | 反例 | 风险 | 更合适的方向 |
  | --- | --- | --- |
  | 把密码直接写进 `docker run -e` | shell 历史和部署记录可能保存 | 应用支持时使用受控 secret 文件 |
  | 把真实 `.env` 提交到仓库 | 历史记录与部署副本扩散 | 提交 `.env.example`，实际值留在受控环境 |
  | 把 `~/.ssh` 整目录挂进容器 | 容器获得私钥和主机信任材料 | 不挂载；为具体任务设计最小凭证 |
  | 把 Docker socket 挂给普通应用 | 应用可能控制整个 Docker daemon | 不授予，除非有经过审计的必要性 |
  | 在日志中打印全部环境变量 | 调试输出可能泄密 | 只打印必要字段并对敏感值脱敏 |
  | 所有服务共享同一管理员令牌 | 单一容器失陷扩大影响 | 每个服务使用最小范围独立凭证 |

  </ComparisonTable>
</section>

<section className="book-section" id="ch8-failures">
  ## 常见失败与判断

  <ComparisonTable>

  | 现象 | 先检查 | 不要立刻做什么 |
  | --- | --- | --- |
  | env 变量为空 | 文件路径、名称、换行和引用方式 | 不要把值再次硬编码进命令 |
  | `.env` 有值但应用没有收到 | Compose 是否配置 `environment` 或 `env_file` | 不要假设 `.env` 自动注入 |
  | inspect 能看到值 | 这是容器环境的可见性边界 | 不要继续放真实秘密验证 |
  | 文件权限过宽 | 所有者和 chmod 结果 | 不要用 777 解决读取问题 |
  | 应用不识别 `_FILE` | 镜像官方文档是否支持 | 不要假设所有镜像都有该约定 |
  | 忽略规则写了但秘密已提交 | Git 历史和远端副本 | 不要只删本地文件，先轮换 |
