  ## 这一章要解决什么

  运行容器只是开始。真正长期维护一套服务时，最危险的时刻往往不是安装，而是“准备更新”“磁盘快满了”或“想把旧东西清掉”。

  本章固定采用下面的顺序：

  <FlowDiagram>
    <div className="flow-node">
      <strong>确认正常</strong>
      <small>配置、状态和本机请求</small>
    </div>
    <div className="flow-node">
      <strong>建立备份</strong>
      <small>项目文件与数据分开处理</small>
    </div>
    <div className="flow-node">
      <strong>验证恢复</strong>
      <small>恢复到新对象，不覆盖原数据</small>
    </div>
    <div className="flow-node">
      <strong>执行更新</strong>
      <small>拉取、重建、逐项验证</small>
    </div>
    <div className="flow-node">
      <strong>核对空间</strong>
      <small>先看占用，再判断对象</small>
    </div>
    <div className="flow-node">
      <strong>精确清理</strong>
      <small>只删除已知名称的练习对象</small>
    </div>
  </FlowDiagram>

  顺序不能颠倒。没有验证过恢复的压缩包，只能叫“生成过一个文件”；没有记录旧镜像的更新，很难在出错时知道要退回哪里；没有逐个核对对象的清理，可能把仍然有价值的数据一起删除。

  <Callout type="danger" title="本章不使用一键清理">
    本章不会执行 `docker system prune`、`docker volume prune` 或 `docker compose down -v`。这些命令可能一次影响多个项目；即使 Docker 把对象标记为 unused，也不代表其中的数据已经没有业务价值。
  </Callout>
</section>

  </InstructionStep>

  <CodeBlock label="备份并列出 Compose 项目" code={createProjectBackup} />

  - 末尾列表同时包含 `compose-web/compose.yaml` 与 `compose-web/site/index.html`；

  - 以只读方式把原 volume 挂到 `/source`；
  - 把备份目录挂到 `/backup`；
  - 在临时容器里用 `tar` 读取数据；
  - 命令结束后由 `--rm` 删除这个临时容器。

<section className="book-section" id="ch11-restore-test">
  ## 第三步：恢复到新 volume 并实际读取

  现在不覆盖原 volume，而是创建 `book03-web-data-restore-test`。这样即使恢复步骤写错，原数据仍然保留。

  <CodeBlock label="恢复并启动只读验证容器" code={restoreVolumeTest} />

  成功状态：

  - 创建了新 volume；
  - 临时恢复命令没有报错；
  - `book03-restore-check` 状态为 Up；
  - curl 返回第 7 章写入 volume 的页面。

  最后一条 curl 最多重试 5 次，每次间隔 2 秒。这样做是因为 `docker run -d` 返回容器 ID 时，Nginx 可能仍在初始化；实机校订中，第一次请求曾收到连接重置，3 秒后同一容器正常返回页面。重试不会把持续失败伪装成成功：全部重试仍失败时，curl 会返回非零状态，此时必须保留原 volume 和归档并继续排查。`--retry-all-errors` 在这里仅用于可重复的本机 HTTP GET 读取；不要把它照搬到上传、支付、创建资源等重复执行可能产生副作用的请求。

  如果 curl 失败：

  1. 运行 `sudo docker logs book03-restore-check`；
  2. 用 `sudo docker inspect book03-restore-check` 核对挂载源；
  3. 再次用 `tar -tzf "$VOLUME_BACKUP"` 查看归档；
  4. 保留原 volume 和归档，不进入清理步骤。

  验证成功后，删除明确命名的验证容器和验证 volume：

  <CodeBlock label="删除恢复验证对象" code={removeRestoreTest} />

  第三条过滤命令应该没有输出；这证明没有容器仍引用验证 volume。最后一条应只返回 `book03-web-data-restore-test`。

  <Callout type="danger" title="只删除 restore-test">
    如果过滤命令仍列出容器，停止，不要执行 volume 删除。这里的目标名称必须完整等于 `book03-web-data-restore-test`，不能换成原始的 `book03-web-data`。
  </Callout>
</section>

  ## 第五步：限制容器日志增长

  Docker Engine 默认常见的 `json-file` 日志驱动不会自动限制文件大小。长时间运行且输出很多日志的容器，可能逐渐占满磁盘。

  本书在 Compose service 中使用 `local` 日志驱动，并限制单个文件和保留文件数。它只影响这一个 service，不改其他项目的 daemon 默认设置。

  打开完整 Compose 文件：

  <CodeBlock label="编辑 Compose 文件" code={editCompose} />

  用下面内容完整替换：

  <CodeBlock label="加入日志限制后的 compose.yaml" code={composeWithLogging} />

  保存后检查配置、重新应用并读取容器真实配置：

  <CodeBlock label="应用并验证日志设置" code={verifyLogging} />

  成功状态：inspect 输出 `driver=local max-size=10m max-file=3`，curl 仍返回页面。

  失败判断：

  - `config -q` 报缩进或字段错误：不要继续 up，回到文件逐行检查；
  - inspect 仍显示 `json-file`：旧容器可能没有被重建，检查 `compose up` 输出和容器 ID；
  - service 起不来：查看 Compose 日志，并可先恢复本章项目压缩包中的 `compose.yaml`；
  - 页面不再返回：核对端口和 bind mount 没有在编辑时丢失。

  <Callout type="warning" title="不要手工删 Docker 日志文件">
    日志文件由 Docker daemon 管理。不要直接进入 Docker 数据目录删除或编辑文件；应通过日志驱动和轮转选项控制增长。
  </Callout>
</section>

<section className="book-section" id="ch11-disk">
  ## 第六步：先看磁盘事实

  <CodeBlock label="查看主机与 Docker 空间占用" code={diskAudit} />

  四条命令分别回答：

  - 根文件系统还有多少空间；
  - 镜像、容器、volume 和构建缓存分别占多少；
  - 每个容器的可写层占用；
  - 当前有哪些 named volume。

  `docker system df` 中的 reclaimable（可回收）是 Docker 根据引用关系估算的，不等于“业务上可以删除”。某个 volume 没有被容器引用，仍然可能是故意保留的离线数据。

  <ComparisonTable>

  | 看起来省事的动作 | 可能影响 | 本书选择 |
  | --- | --- | --- |
  | system prune | 多个项目的 stopped container、network、image 与 cache | 不执行 |
  | volume prune | 所有没有被容器引用的 volume | 不执行 |
  | compose down -v | 当前项目容器、网络和已声明 volume | 不执行 |
  | 按完整名称删除 | 一个已核对对象 | 先备份、恢复验证、过滤引用，再执行 |

  </ComparisonTable>
</section>

<section className="book-section" id="ch11-cleanup">
  ## 第七步：只清理已验证的教学 volume

  `book03-web-data` 来自第 7 章，不被当前 Compose service 使用；它的归档已经创建，并且刚刚恢复到新 volume 验证成功。

  下面三条命令按顺序执行：

  <CodeBlock label="核对并删除已备份教学 volume" code={removeKnownPracticeVolume} />

  判断规则：

  1. 第一条应该没有输出；有输出表示仍有容器引用，立即停止；
  2. 第二条应该只显示名称、挂载点、创建时间等元数据；再次确认 Name 完整等于 `book03-web-data`；
  3. 只有前两项符合预期，才执行第三条；
  4. 第三条只应返回 `book03-web-data`。

  <Callout type="danger" title="删除 volume 会删除其中数据">
    这是本章唯一的数据删除步骤，目标仅限已经备份并验证恢复的教学 volume。真实业务 volume 不能照抄这个决定；必须由数据负责人确认保留期、备份位置和恢复测试。
  </Callout>

  本章结束后：

  - Compose Web service 继续运行；
  - `compose.yaml` 已加入 service 级日志限制；
  - 项目和 volume 归档保留在备份目录；
  - 原教学 volume 已精确删除；
  - 没有执行任何批量 prune；
  - 没有打开新的公网端口。
</section>

<section className="book-section" id="ch11-mistakes">
  ## 常见失败与安全停点

  <ComparisonTable>

  | 现象 | 先判断 | 不要做 |
  | --- | --- | --- |
  | tar 归档打不开 | 文件路径、空间、权限、命令退出状态 | 不要继续删除源数据 |
  | 恢复后页面为空 | 归档内容、恢复目录和挂载目标 | 不要覆盖原 volume |
  | pull 失败 | DNS、网络、仓库、tag 是否存在 | 不要反复重建运行容器 |
  | up 后服务失败 | Compose 配置、状态、日志、挂载 | 不要先删除旧镜像 |
  | 磁盘接近 100% | `system df -v` 与具体对象 | 不要盲目 system prune |
  | volume rm 提示 in use | 找出引用该 volume 的容器 | 不要强制删除或删容器数据 |

  </ComparisonTable>
</section>
