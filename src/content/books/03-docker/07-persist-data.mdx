<section className="book-section" id="ch7-result">
  ## 这一章要解决什么

  镜像是模板，容器有自己的 writable layer（可写层）。应用在容器内创建文件时，如果没有额外挂载，这些文件通常进入当前容器的可写层。

  可写层有两个关键限制：

  1. 它属于这个容器，不是镜像的一部分；
  2. 删除容器时，可写层也随容器一起销毁。

  因此，真实业务不能只因为“文件现在能看到”，就认定数据已经持久保存。Docker 提供多种 mount（挂载）方式，把数据放到容器生命周期之外。

  <ComparisonTable>

  | 位置 | 谁管理 | 删除容器后 | 适合什么 |
  | --- | --- | --- | --- |
  | 容器可写层 | Docker，绑定当前容器 | 数据随容器消失 | 临时文件、可重建状态 |
  | named volume | Docker daemon | 默认继续存在 | 应用生成并长期保存的数据 |
  | bind mount | 服务器文件系统与作者 | 主机文件继续存在 | 需要直接编辑的配置和内容 |
  | tmpfs | 主机内存 | 停止或重启后消失 | 明确不需要落盘的临时数据 |

  </ComparisonTable>

  本章会完成两个独立练习：

  - 用 `book03-web-data` named volume 验证“换容器，数据仍在”；
  - 用 `$HOME/docker-labs/bind-web` bind mount 验证“修改主机文件，容器立即读取新内容”。

  <Callout type="danger" title="持久化不等于备份">
    volume 或主机目录可以让数据跨容器保留，但服务器磁盘损坏、误删 volume、账户被入侵时，数据仍可能丢失。第 11 章才会完成备份与恢复演练。
  </Callout>
</section>

  <Callout type="info" title="mount 会遮住容器目标目录原有内容">
    把 volume 或主机目录挂载到容器某个路径时，那个路径原先来自镜像的内容会被挂载内容遮住。不是原文件被删除，而是容器当前从挂载处看到另一套内容。修复方式通常是用正确挂载重新创建容器。
  </Callout>

<section className="book-section" id="ch7-bind-model">
  ## 第二部分：使用 bind mount

  named volume 适合让 Docker 管理应用数据。但如果你希望直接在服务器上用编辑器修改网页、配置或脚本，bind mount 更直观。

  <ComparisonTable>

  | 问题 | named volume | bind mount |
  | --- | --- | --- |
  | source 写什么 | volume 名称 | 主机文件或目录路径 |
  | 存储位置谁安排 | Docker | 你 |
  | 是否依赖主机目录结构 | 较少 | 是 |
  | 是否适合直接用 nano 编辑 | 不建议直接进 Docker 内部目录 | 是 |
  | 容器默认能否修改 | 通常能 | 默认能，除非设为 readonly |
  | 主机路径不存在时 `--mount` | 不适用 | 报错，不会默默创建 |

  </ComparisonTable>

  bind mount 默认允许容器修改主机文件。对于只需要读取的静态网页，本书会显式使用 `readonly`。

  <Callout type="danger" title="不要把系统根目录或敏感目录挂进练习容器">
    `/`、`/root`、`/etc`、`~/.ssh`、Docker socket 和第二册服务目录都不属于本章 source。可写 bind mount 会让容器进程直接修改主机文件，挂载范围必须尽可能小。
  </Callout>
</section>

<section className="book-section" id="ch7-delete-boundary">
  ## 删除数据前必须回答的五个问题

  无论是 named volume 还是 bind mount，执行删除前都先回答：

  1. source 的精确名称或绝对路径是什么；
  2. 哪个容器或 Compose 项目仍然使用它；
  3. 里面保存的是可重建缓存、配置还是用户数据；
  4. 最近一次可验证备份在哪里；
  5. 删除后如何恢复并确认恢复成功。

  <ComparisonTable>

  | 动作 | 容器 | named volume | bind mount 主机文件 |
  | --- | --- | --- | --- |
  | `docker stop` | 保留 | 保留 | 保留 |
  | `docker rm` | 删除 | 具名 volume 默认保留 | 保留 |
  | `docker compose down` | 删除项目容器和网络 | 默认保留具名 volume | 保留 |
  | 带 volume 删除选项的 down | 删除 | 可能删除 | 通常不删除主机目录 |
  | volume prune | 不直接针对容器 | 可能删除未被引用的 volume | 不处理 |
  | 手工删除主机目录 | 不直接处理 | 不处理 | 直接删除文件 |

  </ComparisonTable>

  <Callout type="danger" title="“没有容器在使用”不等于“数据已经没有价值”">
    停止服务、准备迁移或等待恢复时，volume 可能暂时没有容器引用。不要把 prune 当作磁盘不足时的第一反应。本章保留 `book03-web-data` 正是为了后续完成备份验证。
  </Callout>
</section>

<section className="book-section" id="ch7-failures">
  ## 常见失败与判断

  <ComparisonTable>

  | 现象 | 先检查 | 不要立刻做什么 |
  | --- | --- | --- |
  | 删除容器后页面数据消失 | 新容器是否挂载同一 volume | 不要新建多个随机 volume |
  | 页面变回 Nginx 默认页 | target、volume 名和 source | 不要修改镜像内部文件 |
  | bind source 不存在 | `pwd`、`$HOME`、目录拼写 | 不要换成会默默建目录的简写掩盖错误 |
  | bind 页面 403 或 Permission denied | 主机文件权限和目录遍历权限 | 不要用 `chmod -R 777` |
  | `rw=true` | 是否漏写 `readonly` | 不要假设容器不会修改文件 |
  | volume 无容器引用 | 是否在等待下章或恢复 | 不要立即 prune |
  | 磁盘不足 | 镜像、日志、volume 的明确占用 | 不要执行 system prune 碰运气 |

  </ComparisonTable>
</section>
