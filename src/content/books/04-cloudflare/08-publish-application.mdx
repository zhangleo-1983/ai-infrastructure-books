<section className="book-section" id="book04-ch8-result">
  ## 这一章要完成什么

  第 7 章已经让 `cloudflared` 从服务器主动连接到 Cloudflare，但“Tunnel 已连接”还没有说明哪一个域名应该送到哪一个本地服务。

  本章增加一条 **published application route**。这个词可以理解为“公开应用路由”：

  <FlowDiagram>
    <div className="flow-node">
      <strong>公开主机名</strong>
      <small>https://app.example.com</small>
    </div>
    <div className="flow-node">
      <strong>Cloudflare 边缘</strong>
      <small>接收 DNS 与 HTTPS 请求</small>
    </div>
    <div className="flow-node">
      <strong>生产 Tunnel</strong>
      <small>选择健康 connector</small>
    </div>
    <div className="flow-node">
      <strong>本机源站</strong>
      <small>http://127.0.0.1:8080</small>
    </div>
    <div className="flow-node">
      <strong>Compose web</strong>
      <small>容器内 80/tcp</small>
    </div>
  </FlowDiagram>

  这里的“源站”是 Cloudflare 最终要访问的本地服务。它不是读者浏览器里的地址，也不是 VPS 公网 IPv4。

  <Callout type="info" title="校订日期：2026-08-12">
    Cloudflare 当前官方文档把 published application 定义为“公开主机名到本地服务”的映射，例如 `app.example.com` 到 `http://localhost:8080`。控制台导航和字段名称以后可能变化，正文以字段关系为准。
  </Callout>
</section>

  | 本机服务正常 | `curl 127.0.0.1:8080` 返回页面 | 第三册第 10 章 |

  <CodeBlock
    label="确认本机 Compose 服务"
    code={originCheck}
  />

<section className="book-section" id="book04-ch8-fields">
  ## 先看懂要填写的两个对象

  <InfoGrid columns={2}>
    <section className="info-grid__item">
      <p className="info-grid__title">Public hostname</p>
      <p>用户在浏览器中访问的名称：<code>app.example.com</code>。</p>
    </section>
    <section className="info-grid__item">
      <p className="info-grid__title">Service URL</p>
      <p><code>cloudflared</code> 在服务器本机访问的地址：<code>http://127.0.0.1:8080</code>。</p>
    </section>
  </InfoGrid>

  两边使用不同协议是正常的：

  - 浏览器使用 `https://` 连接 Cloudflare；
  - `cloudflared` 与同一台服务器上的教学服务使用 `http://127.0.0.1:8080`；
  - Tunnel 本身负责 Cloudflare 与 connector 之间的受保护连接；
  - 本章不会给容器内 Nginx 单独签发公网证书。

  <Callout type="warning" title="不要把浏览器地址填进 Service URL">
    Service URL 不是 `https://app.example.com`，否则请求可能再次回到 Cloudflare，形成错误的循环。它也不是 `http://公网 IP:8080`；本机 connector 直接访问回环地址即可。
  </Callout>
</section>

  核对对象名称，而不是只看绿色状态：

    <div className="mock-stack">
      <div className="mock-panel">
        <strong>名称：book04-web</strong>
        <p className="mock-small">用途：第四册教学 Web 服务；不包含账户、IP 或 token。</p>
      </div>
      <div className="mock-panel">
        <span>Connector 状态：</span>{" "}
        <MockStatusBadge tone="success">Healthy · 已连接</MockStatusBadge>

      <div className="mock-panel">
        <span>准备添加：</span>{" "}

  - 打开了别的 Tunnel；

<section className="book-section" id="book04-ch8-hostname">
  ## 第二步：填写 Public hostname

  <InstructionStep number={1} title="Subdomain 填 app">
    `app` 是这一项服务的名字。不要输入完整 URL，也不要包含 `https://`。
  </InstructionStep>

  <InstructionStep number={2} title="Domain 选择自己的域名">
    正文使用 `example.com` 示意。实际页面应从已在 Cloudflare 激活的 zone 中选择，不能手写一个不属于当前账户的域名。
  </InstructionStep>

  <InstructionStep number={3} title="Path 留空">
    留空表示 `app.example.com` 下的所有路径都交给这个服务。第一版不使用按路径拆分多个应用的高级路由。
  </InstructionStep>

  最终公开主机名应当组成：

  ```text
  app + example.com = app.example.com
  ```

  如果 DNS Records 中已经存在 `app` 的 A、AAAA 或 CNAME 记录，先查明用途。不要靠删除旧记录强行通过冲突提示。
</section>

<section className="book-section" id="book04-ch8-service">
  ## 第三步：填写本机 Service

  选择 HTTP，然后填写：

  ```text
  127.0.0.1:8080
  ```

  如果控制台使用一个完整 Service URL 输入框，则填写：

  ```text
  http://127.0.0.1:8080
  ```

  下面是字段关系仿真，不是 Cloudflare 当前版本截图：

  <TunnelRouteMock
    hostname="app.example.com"
    serviceUrl="http://127.0.0.1:8080"
  />

  <ComparisonTable>

  | 填法 | 判断 | 原因 |
  | --- | --- | --- |
  | `http://127.0.0.1:8080` | 正确 | connector 与服务在同一台服务器 |
  | `https://127.0.0.1:8080` | 错误 | 第三册本机服务没有在 8080 提供 HTTPS |
  | `http://0.0.0.0:8080` | 错误 | `0.0.0.0` 是监听含义，不是客户端应连接的目标地址 |
  | `http://公网 IP:8080` | 不使用 | 绕开本机边界，没有必要扩大请求路径 |
  | `https://app.example.com` | 错误 | 把公开入口再次当作源站，可能形成循环 |
  | `http://web:80` | 当前主线不使用 | `cloudflared` 运行在主机而不是 Compose 网络内部 |

  </ComparisonTable>
</section>

<section className="book-section" id="book04-ch8-public-warning">
  ## 保存前：确认这是一条公开入口

  没有 Cloudflare Access 策略、应用登录或其他鉴权时，任何能访问互联网的人都可能打开 `app.example.com`。

  本书当前公开的是没有密码、令牌、个人数据或管理功能的第三册教学静态页。它适合验证域名、DNS、Tunnel 和 HTTPS，不适合直接替换成数据库管理面板或私人 AI 对话记录。

  <Callout type="danger" title="HTTPS 不等于只有你能访问">
    HTTPS 保护传输并帮助浏览器确认访问的主机名，但不会自动要求用户登录。页面含敏感信息时，先停止发布；Cloudflare Access 和应用自身鉴权会在安全边界中另行说明。
  </Callout>
</section>

<section className="book-section" id="book04-ch8-save">
  ## 第四步：保存路由

  保存前逐项朗读最终值：

  <ComparisonTable>

  | 字段 | 本书主线值 |
  | --- | --- |
  | Tunnel | 第 7 章创建且 connector Healthy 的生产 Tunnel |
  | Route type | Published application |
  | Public hostname | `app.example.com` |
  | Path | 留空 |
  | Service type | HTTP |
  | Service URL | `127.0.0.1:8080` |

  </ComparisonTable>

  然后选择 Add route、Save 或当前界面中含义相同的保存操作。

  成功状态不是“按钮消失”，而是：

  - Routes 列表出现 `app.example.com`；
  - 目标显示为 `http://127.0.0.1:8080`；
  - Tunnel connector 仍为 Healthy/Connected；
  - 在 full DNS 设置中，DNS Records 出现指向 Tunnel 的相关记录；
  - 没有要求开放服务器公网 8080。

  失败判断：

  - hostname already exists：同名 DNS 或路由已经存在；
  - domain 不在列表：zone 不属于当前账户或尚未 Active；
  - 保存后 connector 变为 Down：先检查服务器上的 `cloudflared`；
  - 路由已存在但 DNS 没有记录：核对 zone 类型和控制台提示，不要手写随机 Tunnel UUID。
</section>

<section className="book-section" id="book04-ch8-dns">
  ## 第五步：确认 DNS 记录是路由的一部分

  在 Cloudflare 完整 DNS 设置中，从 Tunnel 控制台添加 published application route 时，Cloudflare 会建立把该主机名指向 Tunnel 的 DNS 记录。

  这条记录只说明：

  ```text
  app.example.com 的流量应该交给这个 Tunnel
  ```

  它不说明本机服务一定健康。一个 DNS 记录可以存在，而 connector 或容器仍然离线。

  把这里的上线状态拆成三个对象，会更容易判断故障：

  <ComparisonTable>

  | 对象 | 本章建立或确认的关系 | 单独存在时意味着什么 |
  | --- | --- | --- |
  | DNS 记录 | `app.example.com` 指向当前 Tunnel 的专用目标 | 浏览器能找到 Cloudflare 中的主机名，但 Tunnel 不一定在运行 |
  | Published application route | 把 `app.example.com` 映射到 `http://127.0.0.1:8080` | Cloudflare 知道该主机名应交给哪个本机服务 |
  | Connector | VPS 上的 `cloudflared` 与 Cloudflare 保持连接 | Tunnel 有可用连接，但 DNS、route 和本机服务仍可能配置错误 |

  </ComparisonTable>

  这三个对象不是同一个总开关。Cloudflare 当前官方文档明确说明：DNS 记录与 Tunnel 可以分别存在；如果 Tunnel 停止，DNS 记录不会因此自动删除，访问者可能看到 `1016`。所以“主机名还能解析”不能证明公开入口仍然可用。

  <Callout type="warning" title="不要再额外创建指向 VPS 公网 IP 的同名 A 记录">
    同一个 `app` 主机名同时存在冲突记录，会让请求路径难以判断。Tunnel 主线不需要把 `app.example.com` 直接指向 VPS 公网 IPv4。
  </Callout>
</section>

  返回 VPS 终端：

  <CodeBlock

    code={connectorCheck}

<section className="book-section" id="book04-ch8-failures">
  ## 常见失败先怎样判断

  <ComparisonTable>

  | 现象 | 先判断哪一层 | 不要先做什么 |
  | --- | --- | --- |
  | `nslookup` 显示找不到名称 | DNS 记录和 zone | 不要重启 Docker |
  | 浏览器显示 1033 | Tunnel connector | 不要删除整个 Cloudflare zone |
  | 浏览器显示 1016 | DNS 仍存在，但目标 Tunnel 或其他源站目标不可用 | 不要先重启 Docker；核对 DNS 目标、Tunnel 与 route 是否仍存在 |
  | 浏览器显示 502 | connector 到本机源站 | 不要新增公网 8080 规则 |
  | 本机 `curl` 也失败 | Compose 服务 | 不要反复改 hostname |
  | 返回了错误网站 | hostname、route 或缓存 | 不要忽略内容差异 |
  | 浏览器证书警告 | 主机名与证书状态 | 不要点击忽略后继续 |

  </ComparisonTable>

  第 11 章会把这些现象放进一套完整排错顺序。当前只要能确定失败属于哪一层，就不要用其他层的高风险操作碰运气。
</section>

<section className="book-section" id="book04-ch8-rollback">
  ## 如果现在不准备公开，怎样回退

  回退目标是“停止这一个公开主机名”，不是删除 Compose 数据、域名或整个 Cloudflare 账户。

  在 Tunnel 的 Routes 列表中找到 `app.example.com`，核对目标确实是 `http://127.0.0.1:8080`，再使用当前控制台提供的删除或禁用该 route 的操作。操作后：

  - 检查 Routes 列表不再包含该主机名；
  - 检查 DNS Records 是否仍留有对应记录，并根据当前官方提示处理；
  - 验证外部主机名不再进入该服务；
  - 验证本机 `curl 127.0.0.1:8080` 仍然成功；
  - 不执行 `docker compose down -v`；
  - 不删除域名 zone，也不销毁整个 Tunnel。

  Cloudflare 控制台对 route 删除和 DNS 记录联动的行为可能变化，因此正文不假定 DNS 一定自动删除。每次都以 Records 页面实际状态为证据。
</section>
