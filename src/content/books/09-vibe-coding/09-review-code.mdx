# 评审代码和依赖

每次修改先看 diff，再看新增依赖和网络请求。确认没有把 key 写入前端、没有提交 `.env`，输入内容也没有直接变成危险的 HTML 或命令。

不懂每一行代码，也可以从变化范围、依赖、数据和危险动作开始评审。遇到无法解释的部分，标记出来并请专业开发者检查。

## 先看文件清单

确认本轮只修改项目简报允许的文件。意外出现配置、锁文件、部署脚本或大量删除时，先让 AI 解释，不要直接接受。

## 再看四类高风险变化

| 类别 | 要找什么 |
| --- | --- |
| 秘密 | API Key、密码、令牌、`.env` 内容 |
| 网络 | 新域名、上传、分析脚本、远程字体 |
| 输入 | 直接插入 HTML、拼接命令或路径 |
| 数据 | 新增长期保存、删除、跨用户读取 |

本册原型不联网、不保存数据，因此任何网络请求和持久存储都应视为范围变化。

## 评审新增依赖

记录包名、用途、官方来源、版本、许可证和为什么现有能力不能完成。只为一个小按钮增加大型库时，应要求更轻方案。锁文件变化需要与安装动作一致。

## 要求 AI 解释而不是证明自己正确

```text
请按文件解释本轮变化，特别列出新增依赖、网络请求、存储、
用户输入处理和秘密读取。无法确认的地方标为需要人工评审。
```

## 测试和阅读互相补充

测试证明特定输入下的行为，代码评审寻找测试没有覆盖的风险。两者都通过，仍只支持当前原型范围。

## 本章验收

成功状态是变更文件、依赖、网络、输入和数据风险都能解释，未知项已升级评审。失败判断是测试通过就跳过代码阅读，或把 AI 的自我说明当成唯一安全证据。
