  ## 第一步：固定测试窗口和停止条件

  先写一张不含秘密的测试卡：

  ```text
  测试开始：YYYY-MM-DD HH:mm +08:00
  公开地址：文档只写 https://chat.example.com
  设备 A：电脑 / 浏览器版本
  设备 B：手机 / 移动网络或另一 Wi-Fi
  预期模型：<MODEL_ID>
  计划用户消息：电脑 1 条，手机 1 条
  Direct Connections：关闭
  后台任务：已记录；本次不需要的 Title / Tags / Follow Up / Autocomplete / Query 生成均关闭
  费用上限：<已在提供方设置的小额边界；不写付款资料>
  停止条件：陌生模型、未知用户、用量持续增长、CORS/WS 错误、429 或上游异常
  ```

  在电脑终端执行公开检查：

  <CodeBlock label="电脑侧 DNS 与 HTTPS 预检" code={publicPreflight} />

  在 VPS 执行服务器检查：

  <CodeBlock label="服务器侧应用与 connector 预检" code={serverPreflight} />

  成功状态：DNS 有回答、HTTPS 没有证书错误、应用 healthy、connector active、提供方余额与限额可见。
  任何一项失败都停在第 7 或第 11 章，不用模型请求来测试一个已经失败的浏览器路径。

  Direct Connections 必须继续关闭。否则某台浏览器可能使用保存在本机 local storage 的个人 key 直接请求提供方，
  看起来“同一个模型能回答”，实际却绕过了本书要验证的 Open WebUI 后端连接。

<section className="book-section" id="book05-ch8-desktop">
  ## 第三步：电脑发送第一条公开链路消息

  新建聊天，明确选择预期模型，只发送下面两行：

  <CodeBlock label="电脑端固定测试问题" code={publicTestPrompt} />

  这个问题不含真实域名、IP、账户、客户信息、源代码或内部文档，也明确不需要 Web Search、工具、附件或 RAG。

  观察并记录：

  - 点击发送的时间；
  - 页面是否立即进入生成状态；
  - 文字是否逐步出现，而不是长时间空白后报错；
  - 最终回答是否确实区分浏览器路径与模型路径；
  - 生成结束后按钮是否回到可发送状态；
  - Console 是否出现 CORS 或 WebSocket 403；
  - Network 是否出现异常连续重试；
  - 刷新页面后聊天是否仍在；
  - 重新打开该聊天时，模型与两轮内容是否一致。

  <TerminalMock title="电脑端成功状态示意">
    Browser → Cloudflare → Tunnel → Open WebUI&nbsp;<span className="term-green">通过</span><br />
    Open WebUI → &lt;MODEL_API_BASE_URL&gt;&nbsp;<span className="term-green">通过</span><br />
    流式回答&nbsp;<span className="term-green">连续完成</span><br />
    刷新后聊天&nbsp;<span className="term-green">仍可读取</span><br />
    Console&nbsp;<span className="term-green">无 CORS / WS 错误</span>
  </TerminalMock>

  “回答内容看起来合理”不能替代其他证据。页面可以显示一段缓存内容，但 route、持久化或费用仍可能不符合预期。
</section>

<section className="book-section" id="book05-ch8-mobile">
  ## 第四步：手机使用另一条外部网络验证

  为了避免只验证家中同一 DNS 或同一浏览器状态，手机优先使用移动网络；如果所在地网络不适合，则使用另一条已知合规网络。
  不通过代理绕过模型提供方的地区或服务条款限制。

  按顺序完成：

  1. 手动输入 `https://chat.example.com`，不要从聊天软件中的陌生链接打开；
  2. 核对最终主机名与证书警告；
  3. 使用同一个 Owner 账户登录，不把密码保存到公共设备；
  4. 打开电脑刚创建的聊天，确认同一内容可以读取；
  5. 回到新聊天，选择同一个 allowlist 模型；
  6. 在确认还允许一次付费请求后，只发送：

  <CodeBlock label="手机端固定测试问题" code={mobileTestPrompt} />

  成功状态：输入框、模型选择和发送按钮没有横向溢出；回答能逐步显示；页面滚动、停止生成和重新打开聊天正常；
  手机没有反复登录或空白页面。失败判断：只有 Wi-Fi 能用、手机证书警告、登录循环、模型选择器为空、回答中断或页面无法操作。

  <Callout type="info" title="手机端验证不是性能跑分">
    移动网络延迟会波动。本章只判断功能、可读性与错误边界，不用一次响应时间承诺未来速度，也不连续发送消息制造负载。
  </Callout>
</section>

<section className="book-section" id="book05-ch8-usage">
  ## 第六步：在提供方核对时间窗与实际用量

  等提供方控制台完成正常入账后，只核对必要字段：

  <ComparisonTable>

  | 字段 | 怎样对照 | 异常判断 |
  | --- | --- | --- |
  | 时间与时区 | 落在测试卡记录的开始、结束之间 | 测试前后仍持续增长 |
  | 模型 ID | 与两台设备选定模型一致 | 出现未授权模型 |
  | 请求数量 | 用户消息 2 条，加上可解释的后台任务 | 远多于预期且重复增长 |
  | token / 计量单位 | 与短问题、短回答大致相称 | 异常大且无法由上下文解释 |
  | 费用或额度 | 不超过开始前的小额边界 | 上限未生效或扣费来源不明 |
  | 错误记录 | 无持续 401、429 或 5xx 重试 | 同一请求大量失败重试 |

  </ComparisonTable>

  标题、标签或其他后台能力可能产生额外模型请求，所以“用户点击两次”不一定等于“账单只有两条”。
  但这不是接受任意用量的理由：每一类额外请求都应能由当前启用的功能与同一时间窗解释。

  为了让两台设备的调用能够分开解释，电脑回答结束后先记下时间并等待提供方用量稳定，再开始手机测试；
  手机回答结束后再记录第二个时间点。若两个窗口之间仍不断出现请求，先禁用连接，不把它们笼统归为“后台任务”。

  <Callout type="danger" title="费用或请求来源无法解释时立即停止">
    先在 Open WebUI 禁用该模型连接，再到提供方撤销专用 key，确认用量停止增长。不要只删除聊天记录，也不要连续发送更多消息“看看会不会恢复”。
  </Callout>
</section>

  ## 第七步：给结果下一个有证据的结论

  本章只有三种结论：

  <ComparisonTable>

  | 结论 | 必须满足 | 下一步 |
  | --- | --- | --- |
  | 通过 | 电脑、手机、登录、模型、流式回答、持久化和用量均可解释 | 进入第 9 章收紧用户与隐私 |
  | 部分通过 | 已确定只有某一设备、网络或层级失败 | 保留证据，进入第 11 章对应层 |
  | 停止公开 | 未知用户、费用异常、凭证风险或公开边界错误 | 禁用连接、移除 `chat` route，再调查 |

  </ComparisonTable>

  可以保存“通过/部分通过/停止 + 时间 + 设备类型 + 模型占位符 + 状态码”；不要保存聊天 Cookie、API key、真实用户邮箱、
  完整 provider 账单截图或 Network 中的 Authorization header。
</section>

<section className="book-section" id="book05-ch8-failures">
  ## 常见现象怎样分流

  <ComparisonTable>

  | 现象 | 路径判断 | 首个检查点 |
  | --- | --- | --- |
  | 电脑和手机都打不开 | 浏览器路径共同层 | DNS、证书、route、connector |
  | 电脑能开，手机打不开 | 客户端或网络差异 | 手机 DNS、时间、网络与证书详情 |
  | 能登录但模型为空 | 模型路径尚未开始 | connection enable、allowlist 与角色权限 |
  | 点击发送后 401 / 403 | 模型连接认证或授权 | key、endpoint、账户与地区政策 |
  | 点击发送后 429 | 提供方速率或费用边界 | 余额、限额、并发与重试 |
  | 回答开始后中断 | 流式链路 | Console、WS/SSE、CORS 与上游超时 |
  | 刷新后聊天消失 | 应用持久化 | named volume、写入错误与当前账户 |
  | 用量远高于两条消息 | 后台任务或异常调用 | 时间窗、任务模型、连接使用者与 key |

  </ComparisonTable>
</section>
