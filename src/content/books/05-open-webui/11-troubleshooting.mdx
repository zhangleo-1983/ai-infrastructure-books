<section className="book-section" id="book05-ch11-purpose">
  ## “模型不回答”不是一个根因

  <OpenWebUIPathMap labelId="book05-chapter-11-path-title" />

  一个现象可能同时包含多个层级：

  - 页面完全打不开：路径 A 先失败；
  - 页面能开但不能登录：路径 A 已到 Open WebUI，问题可能在应用认证或 Cookie；
  - 可以登录但模型列表为空：路径 A 成功，路径 B 在连接或模型发现阶段失败；
  - 模型可选但发送后报错：路径 B 已开始，问题可能在 key、模型 ID、额度或上游；
  - 回答开始后中断：还要检查 WebSocket、SSE（服务器持续推送事件）、代理超时和提供方流式格式。

  排错只追求两个结果：

  1. 找到哪条路径、哪一层第一次偏离已知正常状态；
  2. 用一条状态、请求结果或日志证明判断。

  <Callout type="danger" title="先保存证据，不要先 restart">
    重启可能改变日志时间线，轮换 key 会增加变量，删除 volume 更可能永久丢失账户和聊天。先记录现象，再修改一层；每次修改后用同一组检查复测。
  </Callout>
</section>

  <ComparisonTable>

  | 用户看到的现象 | 第一条路径判断 | 先查哪一层 |
  | --- | --- | --- |
  | `NXDOMAIN` 或找不到主机名 | 路径 A 未到 Cloudflare 应用入口 | DNS 与 route |
  | Cloudflare Error 1033 | 路径 A 到边缘，但没有可用 Tunnel connector | cloudflared |
  | 500 / 502 或其他源站连接错误 | connector 无法访问本机 Open WebUI | route、回环端口与容器 |
  | 登录页正常，登录后循环 | 路径 A 到应用，认证状态未保持 | Cookie、URL、Secret 与时间 |
  | 登录正常，模型列表为空 | 路径 B 在模型发现前失败 | Connections、base URL、allowlist |
  | 只有某台浏览器出现额外模型 | 可能启用了个人 Direct Connections | 管理员全局开关与该浏览器 User Settings |
  | 401 / 403 | 可能是应用登录，也可能是上游模型鉴权 | 先确认哪一个请求返回错误 |
  | 404 / model not found | 模型路径或 ID 不匹配 | base URL、API path、模型 ID |
  | 429 | 上游限速、余额或支出上限 | 提供方用量与限制 |
  | 回答开始后中断 | 流式链路不完整 | CORS、WebSocket、SSE、超时或上游格式 |

  </ComparisonTable>

<section className="book-section" id="book05-ch11-ssh-browser-boundary">
  ## 公开加固后，SSH 浏览器页面不再是等价对照

  第 7 章已经把 `CORS_ALLOW_ORIGIN` 收紧到唯一公开 HTTPS Origin，并启用了 Secure Cookie。
  此时通过 SSH 转发打开 `http://127.0.0.1:3000`，登录或 WebSocket 失败可能正是这些安全设置在生效，
  不能据此断定 Open WebUI 后端已经损坏。

  <ComparisonTable>

  | 对照方式 | 能证明什么 | 不能证明什么 |
  | --- | --- | --- |
  | VPS 上请求 `/health` | 应用进程与健康 endpoint 可响应 | 登录、模型或公开代理正常 |
  | VPS 上请求 `/api/config` | 后端 HTTP 接口可响应 | 浏览器 Cookie、CORS 与流式链路正常 |
  | 公开 HTTPS 浏览器 | 当前支持的真实 Origin、登录与前端链路 | 跳过 Tunnel 后的本机浏览器体验 |
  | 临时放宽 CORS / Secure Cookie | 会改变故障现场 | 不能作为第一步诊断 |

  </ComparisonTable>

  因此，本书排错先比较“VPS 本机只读 HTTP 探针”和“公开 HTTPS 浏览器”，不临时增加 `localhost`
  Origin，也不关闭 Secure Cookie。确实需要隔离浏览器测试时，应另建维护窗口和可回退配置，测试后恢复唯一
  公开 Origin；不能在故障中顺手把允许范围永久放宽。
</section>

  ## 第六步：只读取必要的应用日志

  本机检查失败，或模型请求失败但页面仍能打开时，读取最近 80 行：

  <CodeBlock
    label="读取带时间戳的 Open WebUI 日志"
    code={appLogs}

  对照故障发生时间寻找：

  - 容器启动与数据库迁移错误；

  - 登录 token、Cookie 或 Secret 相关错误；

<section className="book-section" id="book05-ch11-symptoms">
  ## 八类典型故障

  <TroubleshootingItem title="1. 页面完全打不开：NXDOMAIN、1033 或 5xx" open={true}>
    <p><strong>先判断：</strong>这是路径 A，不是模型连接问题。</p>
    <ul>
      <li>NXDOMAIN：检查 `chat` route、DNS 记录和 zone；</li>
      <li>1033：检查目标 Tunnel 与 Healthy connector；</li>
      <li>500、502 等连接错误：检查 route 是否仍指向 <code>http://127.0.0.1:3000</code>，再运行本机 <code>curl</code>；</li>
      <li>本机也失败：转向 Compose 状态、监听与日志。</li>
    </ul>
    <p><strong>不要先做：</strong>开放公网 3000、删除整个 zone、重建模型 key。</p>
    <p><strong>2026-09-11 RC 实测：</strong>把唯一教学 route 短时指向明确未监听的回环端口后，
      本次页面显示 <code>500 Internal Error</code>；恢复 3000 后登录页立即恢复。错误码会受边缘与 connector
      版本影响，不能把所有源站连接失败写死为 502。</p>
  </TroubleshootingItem>

  <TroubleshootingItem title="2. 能看到登录页，但登录后循环或立即退出">
    <p><strong>先判断：</strong>公开 URL、Cookie、服务器时间或登录 Secret 是否在容器重建后改变。</p>
    <ul>
      <li>确认浏览器始终使用同一个 <code>https://chat.example.com</code>；</li>
      <li>核对 <code>WEBUI_URL</code> 与 CORS 允许的 Origin；</li>
      <li>HTTPS 部署应使用 Secure Cookie；</li>
      <li>检查 VPS 时间是否正确；</li>
      <li>如果刚重建容器，核对 <code>WEBUI_SECRET_KEY</code> 是否仍为原持久值。</li>
    </ul>
    <p><strong>成功状态：</strong>同一账户刷新后仍保持登录。更换 Secret 会使现有会话失效，需要重新登录；不要把 Secret 贴进日志求助。</p>
  </TroubleshootingItem>

  <TroubleshootingItem title="3. 登录正常，但模型列表为空或加载很久">
    <p><strong>先判断：</strong>Connections 中的连接是否 Enabled、base URL 是否可达、提供方是否支持 <code>/models</code>。</p>
    <ul>
      <li>如果 URL 保存后导致模型列表卡住，先 Disable 该连接；</li>
      <li>核对 URL 是否包含提供方要求的 <code>/v1</code>；</li>
      <li>聚合提供方返回大量模型时，使用 Model IDs Filter；</li>
      <li>只有一台浏览器出现额外模型时，检查 Direct Connections 与该浏览器 local storage，不要修改服务器 allowlist；</li>
      <li>只有提供方官方说明允许时，才用精确模型 ID 绕过模型自动发现。</li>
    </ul>
    <p><strong>不要先做：</strong>删除 Open WebUI volume 或随机添加模型名称。</p>
  </TroubleshootingItem>

  <TroubleshootingItem title="4. 模型请求返回 401 或 403">
    <p><strong>先确认谁返回错误：</strong>登录接口的 401 属于 Open WebUI；模型请求日志中的上游 401/403 属于模型连接。</p>
    <ul>
      <li>401 常见于 key 过期、被撤销、粘贴不完整或 endpoint 不匹配；</li>
      <li>403 常见于权限、模型授权、账户状态或地区策略；</li>
      <li>若提供方的 <code>/models</code> 使用非标准认证，单独查其官方兼容说明。</li>
    </ul>
    <p><strong>修复原则：</strong>只更正当前连接或轮换专用 key；不关闭 Open WebUI 登录，不绕过提供方政策。</p>
  </TroubleshootingItem>

  <TroubleshootingItem title="5. 返回 404、model not found 或错误模型">
    <p><strong>先核对三项：</strong>base URL、API 类型、精确模型 ID。</p>
    <ul>
      <li>提供方首页不是 API endpoint；</li>
      <li>Chat Completions 与 Responses 不是同一个 API 类型；</li>
      <li>模型显示名不一定等于接口 model ID；</li>
      <li>Prefix ID 会改变 Open WebUI 中显示和选择的模型名称。</li>
    </ul>
    <p><strong>不要先做：</strong>随机切换几十个模型。每次只改一项，并用同一个无敏感测试问题复测。</p>
    <p><strong>2026-09-11 RC 实测：</strong>临时把 allowlist 改为一个明确不存在的占位模型后，页面返回了
      支持模型列表与传入 ID 不一致的错误；恢复唯一正确 ID 后模型选择器回到单模型基线。该错误在进入提供方
      计费请求前就被识别，因此提供方用量没有增加。</p>
  </TroubleshootingItem>

  <TroubleshootingItem title="6. 返回 429、额度不足或请求数异常">
    <p><strong>先到提供方核对：</strong>余额、速率限制、并发、模型单价、支出上限与请求时间。</p>
    <ul>
      <li>停止快速连续重试；</li>
      <li>检查标题、标签等后台任务是否产生额外请求；</li>
      <li>确认没有未知用户或公开注册；</li>
      <li>费用持续增长时先 Disable 连接并撤销专用 key。</li>
    </ul>
    <p><strong>停止条件：</strong>需要充值、提高额度或升级套餐时，进入费用闸门，不能把它当作普通排错动作。</p>
  </TroubleshootingItem>

  <TroubleshootingItem title="7. 回答开始后中断、显示空白或 WebSocket 403">
    <p><strong>先判断：</strong>浏览器控制台是否出现 CORS、WebSocket、mixed content 或流式解析错误。</p>
    <ul>
      <li><code>WEBUI_URL</code> 应对应公开 HTTPS 地址；</li>
      <li><code>CORS_ALLOW_ORIGIN</code> 应包含当前真正支持的精确访问 Origin；</li>
      <li>代理链必须支持 WebSocket upgrade 与 SSE 流式响应；</li>
      <li>长回答需要足够的上游与代理超时；</li>
      <li>提供方响应格式偏离 Chat Completions schema 时，普通聊天可能成功而工具或流式回答失败。</li>
    </ul>
    <p><strong>对照方法：</strong>先在 VPS 用 <code>/health</code> 与 <code>/api/config</code> 检查本机后端，再通过公开域名测试浏览器。不要把公开加固后的 HTTP SSH 页面当作等价登录对照，也不要为排错临时关闭 Secure Cookie。</p>
  </TroubleshootingItem>

  <TroubleshootingItem title="8. 更新后要求重新注册、聊天消失或数据库报错">
    <p><strong>先判断：</strong>当前容器是否仍挂载 <code>book05-open-webui-data</code>、原 <code>WEBUI_SECRET_KEY</code> 是否保留，以及新版本是否已经执行数据库迁移。</p>
    <ul>
      <li>要求重新创建管理员通常意味着挂载了空 volume，不能顺手再注册一个账户；</li>

      <li>数据库 migration 报错时，保留日志和失败现场，不连续重启；</li>
      <li>按第 10 章在新的测试 volume 中验证“旧固定镜像 + 更新前归档 + 原 Secret”；</li>
      <li>production 恢复会覆盖更新后数据，必须另行确认时间点和目标。</li>
    </ul>
    <p><strong>不要先做：</strong>对 live volume 运行清空命令，或只把镜像标签改回旧版并假设数据库也会自动降级。</p>

<section className="book-section" id="book05-ch11-localhost">
  ## 一个特别常见的容器误区：localhost 指向谁？

  如果模型服务运行在 VPS 主机上，而 Open WebUI 运行在容器中，管理员连接里填写 `http://localhost:…`
  通常会让 Open WebUI 容器连接它自己，而不是 VPS 主机。

  <ComparisonTable>

  | 地址出现在哪里 | `localhost` 指向谁 | 应怎样处理 |
  | --- | --- | --- |
  | VPS shell | VPS 主机 | 可以检查主机服务 |
  | Open WebUI 容器 | Open WebUI 容器自身 | 不能假设能访问主机服务 |
  | 同一 Compose 网络 | 仍是当前容器 | 使用目标 service name 和容器端口 |
  | 远程 HTTPS 模型 API | 不使用 localhost | 使用提供方官方 base URL |

  </ComparisonTable>

  本书主线使用远程 HTTPS API，不需要解决本机模型网络。如果以后在附录实验 Ollama，必须重新画出容器网络，
  不能把当前远程接口的结论直接套用。
</section>

  ## 第七步：一次只修一层

  <ComparisonTable>

  | 已证明的失败层 | 一项最小修复 | 修复后立即复测 |
  | --- | --- | --- |
  | connector inactive | 恢复既有 cloudflared 服务 | systemd → 本机应用 → 公开 HTTPS |
  | route 指错端口 | 改回 `127.0.0.1:3000` | 本机 API → 公开登录页 |
  | 容器停止 | 查日志后恢复既有 Compose service | `ps` → 本机 API → HTTPS |

  不要把“更新镜像”“删除 volume”“关闭防火墙”“关闭登录”和“重新创建整个 Tunnel”当作通用修复。

<section className="book-section" id="book05-ch11-escalation">
  ## 什么时候应该停止并升级求助

  出现以下情况不要继续试错：

  - volume、数据库或迁移错误，且没有可验证的更新前备份；
  - 管理员账户身份不明，或出现未知管理员；
  - API key、Cookie、Secret 或用户数据已经公开泄露；
  - 模型用量持续增加，无法确认来源；
  - 需要恢复会覆盖现有聊天，但尚未确认备份时间点；
  - 需要提高模型额度、升级 VPS 或购买额外资源；
  - 计划修改 Cloudflare zone、删除 Tunnel、删除 volume 或销毁 VPS；
  - 涉及组织数据、监管义务或账户争议。

  求助时提供脱敏后的：时间、版本、现象、第一处失败层、最小命令结果、最近变更和已经尝试的一项修复。
  不提供完整日志、数据库、真实聊天、API key、Tunnel token、Cookie 或账户恢复材料。
</section>
